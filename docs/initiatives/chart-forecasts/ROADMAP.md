# Chart forecasts and forward-ledger evaluation

Status: implementation plan; product code has not been changed.
Prepared 2026-09-05 using FORGE plan mode.

## Product contract

The operator manually requests a forecast for the chart they are inspecting. The model
can commit to a TA trade setup, plot entry/stop/targets and explanatory zones, and have
CopeNet evaluate subsequent prices. The existing Ledger is the product home for outcomes.

The founder's constraints are explicit:

- Forecast generation is manual and per chart. No universe forecasting, scheduled model
  calls, automatic ticker selection, or forecasts generated by ordinary page loads.
- Tracking after registration is deterministic and automatic while the host and the
  explicitly configured price schedule are running.
- These are simulated trades and forward predictions. There is no broker order path.
- Original calls remain inspectable, including failures, abstentions, unfilled entries,
  ambiguous candles and later amendments.
- Compare direction at four/eight weeks with the current ledger, and evaluate entry/exit
  planning separately. A trade's stop-out cannot be erased by a later price recovery.
- Keep the compact mobile composer. Put the deliberate forecast action in its existing
  options surface; display a temporary mode indicator only while requesting a forecast.

The acceptance story: manually request one setup, see its registered levels on the chart,
leave the page, ingest later daily bars, and return to a ledger entry explaining entry,
target/stop/expiry events and four/eight-week direction with exact source evidence.

Important gaps found in code:

1. `resolve_due_claims()` uses the latest cached close when an overdue horizon is checked.
   A late check can therefore score a different date. Do not reuse it as the forecast
   event evaluator or silently overwrite historical ledger outcomes.
2. Existing chart objects are independent editable levels/zones/lines/labels. Their
   mutation/undo contract is unsuitable as the authority for a registered trade.
3. `ChartStore.cleanup_orphans()` currently retains resources only through observation
   references. New forecast evidence references must participate in retention and capacity.
4. Captured candle metadata currently declares basis but not the cache's split fingerprint
   or exchange-session completion information. Forward tracking needs explicit provenance;
   obtaining it must not refetch or replace the browser's captured rows.
5. `LaneTurnSpec` currently has no chart-context binding. Pairing requires an explicit,
   typed extension through the ordinary harness, preserving per-session observation access.
6. The existing scan resolver includes VOO as context for price scans. Disclose this one
   benchmark dependency in scope previews; it never becomes a forecast candidate.

## Recommended first-release scope

US-listed equities/ETFs with supported exchange-calendar and split-only price history.
Analysis can use D/W/M chart evidence; simulation uses completed daily OHLCV.

| Choice | Proposed rule |
| --- | --- |
| Direction | Long or short; the model may return `no_setup` with a reason |
| Entry | One exact level, either pullback limit or breakout stop; optional entry zone is explanatory and must name its exact executable level |
| Stop | One fixed protective stop; no trailing/breakeven automation in this release |
| Targets | One to three ordered targets with explicit exit fractions totaling 100%; default one target, 100% |
| Zones | Up to four labeled context/invalidation zones, distinct from executable conditions |
| Entry expiry | Default 10 eligible exchange sessions after activation; shown before request and recorded immutably |
| Forecast deadline | Eight calendar weeks (56 days) after publication, independent of when entry occurs |
| Direction score | Four/eight calendar weeks from publication, common reference/endpoint convention described below |
| Position size | One normalized unit; no account balance, leverage, dollar allocation or live holding required |
| Costs | Gross simulated price P&L; fees, spread, borrow and dividend cash flows excluded and labeled |
| Amendments | Append a dated amendment; original model track record continues under original rules |
| Comparison | Historical ledger context always available; isolated paired mode is an explicit extra-model-run option, recommended for cleaner experiments |

Entry/stop/target ordering is validated by direction. Prices must be positive and finite,
entry-to-stop risk nonzero, fractions positive, and targets distinct and correctly ordered.
Unknown price basis, unavailable provenance or unsupported instrument blocks registration
with an actionable explanation. Stale evidence may be discussed, but admission requires
freshness/completion provenance and agreement with the captured data revision. Ordinary
quotes arriving during generation do not invalidate that frozen evidence. If a split or
source correction makes its price basis incompatible before publication, fail visibly and
offer a new capture without rerunning silently.

Partial exits are included because multiple take-profit levels otherwise imply execution
that the system cannot define. Additional zones remain annotations, never inferred orders.
Continuous forecast paths, dynamic stops, intraday monitoring, crypto, real executions,
automatic model commentary and a broad performance-evaluation platform are later work.

## Manual request and publication UX

1. **Forecast this chart** opens a small request sheet: current ticker, selected evidence
   range, model/detail, entry expiry, eight-week deadline, optional paired comparison and
   tracking schedule. Explain that a valid returned setup is recorded automatically.
2. **Record forecast** submits a typed, operator-issued request ID and frozen observation.
   This explicit action grants only the bound forecast capability. Natural-language chat
   can discuss setups; it cannot independently authorize a tracked forecast or expand scope.
3. The model inspects immutable evidence and submits one structured result. The server
   validates and records it before exposing the completed forecast. Do not scrape prose,
   infer levels from labels, or select the most attractive result from multiple candidates.
4. Valid publication records the server clock, draws the forecast and opens its compact
   summary. `no_setup`, rejected output, cancelled and failed attempts also remain logged.
   A failed pair is visibly incomplete; a valid member remains frozen and available.
5. **View in Ledger** opens the forecast row. Entry/stop/target interactions open the same
   record, including evidence, source run, methodology, event timeline and amendments.

Request lifecycle: `requested → generating → published | no_setup | failed | cancelled`.
Persist admission before invoking a provider. Retry of the same ID returns the existing
attempt or status; uncertain execution never dispatches a second provider run automatically.
Bound repair attempts may fix schema errors within the same admitted run; preserve their
count. There is only one final valid submission per lane, enforced server-side.

One active forecast request per chart session; the normal session lock applies. Stop
cancels every active lane for that request. Reconnect resumes status observation, not
generation. Switching ticker does not retarget an in-flight request. A paused/closed host
is shown as delayed tracking, never as continuously watching the market.

The saved-versus-rendered distinction remains explicit. Chart navigation, hidden panes,
comparison mode, incompatible basis and missing anchor positions can hide an overlay
without deleting or completing the underlying forecast.

## Domain and persistence

Add focused `core/market/forecasts/` modules. Keep one canonical forecast vocabulary across
RPC, tools, storage, rendering and reporting.

| Record | Required contents |
| --- | --- |
| Request | Request ID, operator intent, originating session/document, observation ID, requested model/detail, comparison mode, exact tracking admission, generation status |
| Forecast | Forecast ID, request/lane ID, instrument identity, evidence cutoff/capturedAt/publishedAt, analysis timeframe, direction, thesis, entry type/price, stop, target prices/fractions, zones, entry expiry, deadline, four/eight-week due times, evidence references |
| Attribution | Provider/model, run/session IDs, prompt version/hash, evidence manifest hash, initial presentation hash, reported usage or unknown, source basis/fingerprint and evaluation-policy version |
| Pair member | Pair/request ID, lane role (`directional` or `ta`), bullish/bearish/neutral/abstain result, rationale, completion status and immutable output; setup fields belong only to the TA member |
| Evaluation event | Stable event ID, forecast ID, event type, session date, recordedAt, source evidence ID, before/after state, price, exited fraction, reason and evaluator version |
| Evaluation snapshot | Exact consumed daily bars, source/fetch timestamp, calendar/session metadata, split fingerprint, hash and coverage |
| Amendment | Parent forecast ID, author/operator-or-model provenance, time, changed fields, rationale; never overwrites original levels or attributed score |

Recommended storage: forecast tables in the existing `chart-workspace.sqlite3`, accessed by
a composed `ForecastStore` using `ChartStore.connect()`. Keep forecasting logic out of the
drawing mixins. This permits transactional publication plus evidence retention and avoids
cross-database dual writes. Existing directional ledger JSON remains its canonical record;
the Ledger API composes their distinct report types without duplicating forecasts there.

Use immutable published bodies and append-only events, with a rebuildable current-state
projection. Add foreign keys and unique constraints on request/lane and event identity.
All record/event/evidence writes and state advancement use one transaction. Include new
tables in `_used_bytes`; capacity failure leaves prior evidence and evaluations intact.
Extend cleanup to retain resources referenced by observations OR forecast evidence. Pin
admitted observations before generation; retain failed-attempt metadata without unlimited
unbound payload retention. No implicit deletion of registered forecasts or their evidence.

Acquisition metadata must describe the same revision rendered by `useTickerViewModel`:
contribute cache identity, split fingerprint and completed-session provenance through the
existing ticker transport/viewState path. Validate agreement at admission; do not enrich
the snapshot by quietly fetching newer candles. Generated forecasts and their render state
contribute a typed `panel:forecasts` resource with explicit account scope and coverage.

## Deterministic daily-bar evaluator

Implement a pure function over an immutable forecast, prior state and ordered eligible
bars. Persistence, acquisition, delivery and model execution remain outside that function.
Freeze these rules as `daily-ohlcv-1`; different later rules form a separate score cohort.

### Time eligibility

- Activation is the first exchange-session open strictly after publication. A forecast
  published during a session cannot use that day's earlier high/low as a future fill.
- Only fully fetched completed daily bars are evaluated. Reuse exchange-calendar logic,
  including holidays, early closes and DST; bar midnight labels are not availability times.
- Walk every eligible session from the last processed point, including after host downtime.
  No last-close shortcut and no retroactive trigger using a pre-publication candle.
- An entry is allowed through its recorded expiry session. At that session close, an
  unentered setup becomes `expired_unfilled`. If the hard forecast deadline falls earlier,
  the deadline wins. Partially realized positions keep their existing protective stop.
- For the eight-week deadline use the last scheduled session close at or before the due
  instant. Close remaining simulated exposure there, after eligible stop/target processing.
  Determine that session from the calendar; do not fall back to an older available bar.
- Missing required sessions block progression at the gap. Completion is never inferred
  from absence of fresh data. Preserve proven earlier events and expose `data_gap`/`stale`.

### Price-touch and fill conventions

For a long setup (short is the exact mirror):

| Event | Rule |
| --- | --- |
| Limit entry | If open <= entry, simulated fill at open; otherwise low <= entry records an intrabar entry at the level |
| Stop entry | If open >= entry, simulated fill at open; otherwise high >= entry records an intrabar entry at the level |
| Existing-position stop | If open <= stop, exit remaining size at open; otherwise low <= stop implies a level-price stop touch |
| Profit target | If open >= target, fill that fraction at the target price (conservative no-gap-improvement convention); otherwise high >= target implies a target touch |

The trade engine records *simulated* fills under these conventions. An OHLC touch is not
evidence of an actual executable order fill, queue position, liquidity or intrabar timing.

- Process the open first for a position carried into the bar. If an opening stop exits
  the trade, later range movement cannot revive it. If opening targets fill partial size,
  reduce size before considering the remaining intrabar conditions.
- If a new opening entry lands at/beyond its protective stop or any profit target, record
  `gapped_past_setup` and skip entry. Do not invent a profitable immediate round trip.
- For a position active at the open, when the remaining range touches both stop and an
  unfilled target and their order changes realized P&L, record `ambiguous`.
- The first policy conservatively classifies any intrabar entry plus a same-bar candidate
  exit as `ambiguous`. This deliberately forgoes some cases that more sophisticated path
  inference could resolve. Do not assume entry happened before the day's high or quietly
  choose an optimistic path. Report these exclusions separately from carried-position
  stop/target ambiguity so a later policy can be evaluated against the same evidence.
- Multiple targets on the favorable side fill in price order when entry precedes the bar
  and no conflicting stop is touched. Exit fractions are fractions of the original unit.
- On ambiguity, stop claiming a unique simulated trade result. Retain the known partial
  events and the offending candle; directional horizon scoring can still continue.
  Scenario bounds or conservative alternative scores are deferred, not mixed into wins.

Trade state: `waiting_entry → active → target_complete | stopped | deadline_exit`.
Other terminal classifications: `expired_unfilled`, `gapped_past_setup`, `ambiguous`.
Data/tracking health is a separate field (`ready`, `stale`, `data_gap`, `revision_review`,
`tracking_paused`, `unsupported`) so a fetch failure cannot become a trade outcome.

Define planned risk per original unit as `abs(entryLevel - stopLevel)`. Gross R is signed,
fraction-weighted exit-minus-actual-entry P&L divided by that frozen planned risk; label
it **planned-risk R**. Preserve actual simulated entry and gap effects. A stop gap can
lose more than 1R. Unfilled or ambiguous trades have no invented zero-R realized result.
Track holding duration and exit fractions; defer exact intrabar excursion statistics when
daily bars cannot establish whether an extreme occurred before entry or after exit.

### Splits and historical revisions

Preserve original published levels, evaluation candles and fingerprints. A later split
changes the cache's historical price basis. Normalize new cache bars back into the frozen
publication basis using recorded post-publication split factors before comparing levels
or returns; expose current-basis display equivalents without mutating the original setup.
Use the shared split history, not a second vendor adjustment implementation. Missing or
contradictory action history sets `revision_review` and blocks further scoring.

If already-consumed history changes, preserve the earlier evaluation and append a revision
notice. Build any corrected replay as an explicitly versioned evaluation; never silently
overwrite a published result or combine old and corrected bars in one state transition.

## Directional comparison and honest scorecards

Every valid TA setup also records a directional forecast. `no_setup` is an abstention,
counted in coverage. Direction uses the last completed close in the admitted frozen
evidence as its reference and the scheduled session close at/before each 28/56-day due instant as
its endpoint. Use split-consistent prices. This is a price-return convention; label it.
Future price paths begin after publication even though the reference close may be older.

New direction scores: bullish correct if return > 0; bearish correct if return < 0;
neutral or exactly flat is a push. Publish the rule version. Existing ledger outcomes
remain under their original rules and retain their recorded evaluation dates/basis.

Show three comparisons with different meanings:

1. **Historical ledger context:** display existing ticker-lean results alongside chart
   direction, filtered by model/horizon and showing date range, sample and source cohort.
   Different selected tickers, eras, price bases and endpoint rules preclude a causal
   "TA improved accuracy" claim. Existing screen/attention/regime kinds remain separate.
2. **Paired directional experiment (recommended opt-in):** on one manual request, run a
   plain direction lane and a TA setup lane against the same frozen evidence. Use the
   same provider/model settings, initial packet and exact-read limits; record actual
   usage and reads because identical budgets do not imply identical consumption.
3. **Trade planning:** activation rate, stop/target/deadline counts, planned-risk R, holding
   time, unresolved/ambiguous/unfilled fractions and sample size. Do not compare trade
   win rate directly with directional hit rate or invent a trade strategy for the plain lane.

Paired mode adds one separately attributable model run. It is visible in the request sheet;
no extra provider call occurs without choosing that mode. Both lanes start with clean
isolated sessions, the same explicit evidence, no prior chart conversation or private
profile injection, and no access to the other's answer. This compares prompting/workflow
on a matched input, not the exact older `market.interpret` pipeline.

Adapt the existing directional prompt to this frozen-input contract and version it. Share
content-addressed resources through separately session-bound observation headers; never
weaken `observation(session_key)` authorization to let a lane read arbitrary observations.
Compare semantic evidence hashes separately from lane-specific session/observation IDs;
different authorization envelopes must not be mistaken for different source evidence.
Exclude both lanes' newly produced results from their shared input. Persist each member's
output before revealing either. Set one pair publication/activation clock after completion.
If one lane fails, mark the pair incomplete and retain the valid member with its actual
publication clock; never backdate a later replacement into that pair.

Primary paired score uses the same eligible pairs at each horizon: both correct, TA only
correct, plain only correct, both incorrect, with neutral/abstained/missing pairs shown
separately. Report paired count and correctness delta, not a winner badge based on a few
trades. Multiple manual requests on the same ticker may be correlated; show their count
and distinct ticker/date coverage. All admitted attempts, including reruns and failures,
remain countable; hiding an overlay or withdrawing attention does not delete a loss.

## Tracking, tools and transport

Use the existing scan scheduler for prices only. A focused forecast schedule has explicit
symbols, `includeUniverse=false`, no watchlist expansion, `publishBrief=false`,
`interpret=false`. Recommend weekdays at 17:00 America/New_York. Expose the existing VOO
context acquisition in its preview; no universe or benchmark predictions are generated.

Adding a forecast ticker to acquisition is a visible scope change in the manual request
sheet, admitted through the existing scan preview/revision contract. Reuse a suitable
existing focused scan when possible. Failure to configure tracking leaves a durable
forecast visibly `tracking_paused`; repair tracking without regenerating its prediction.
Pausing generation and pausing price acquisition are distinct. A page load may read and
evaluate already-cached data, but must never start network acquisition or an LLM run.

After a price scan, evaluate only registered forecasts for acquired symbols and applicable
scan bindings. Process cached historical catch-up without requiring the model. Extend the
post-price integration with separately inspectable forecast results; do not overwrite
`triggerEvents` or translate a multi-stage trade into independent one-shot alert rules.
Notifications are deferred; existing delivery consent applies if added later.

Proposed exact contracts (final names should remain canonical across all layers):

| Surface | Operation |
| --- | --- |
| Operator RPC | `market.forecast.request`, `.get`, `.list`, `.cancel`, `.amend`, `.tracking.update`; cancel aborts an unfinished request and never deletes a published forecast |
| Model tool | `market.forecast.submit`: discriminated directional/setup/no-setup result, bound to an admitted request and permitted lane role; one valid commit |
| Model tool | `market.forecast.read`: scoped forecast/events/evidence with bounded rows and pagination |
| Operator RPC | `market.forecast.rendered`: forecast revision/view/basis and rendered/hidden/failed receipt |
| Server event | `market.forecast.updated`: stable forecast ID and revision; clients reconcile from stored state |
| Existing Ledger RPC | Extend `market.ledger.get` with a typed `forecasts` report; keep existing claim fields and meanings |

Read-only chart access alone cannot submit a forecast. Request intent is server-owned,
never guessed from model prose or tool arguments. Bind provider/model attribution,
instrument, observation and publication clock on the server. Preserve chart-only scope,
account exclusion, annotation ownership, normal Barricade/approval behavior and explicit
Market session routing. Register descriptor, policy, bounded model body and inspectable
preview/artifact together. Never add an unrendered custom preview type.

## Chart and Ledger presentation

Forecast overlays derive directly from the published forecast and its evaluation events.
They are selectable, hideable and inspectable; they are not ordinary draggable drawing
objects. Draft/amendment editing is explicit and produces a new record. Manual drawing
undo never removes a forecast or changes its score. Keep original/model versus operator
amendment attribution clear in both surfaces.

Reuse the existing drawing geometry/paint helpers through a focused forecast overlay
adapter. Reuse exchange-candle index and pane-relative positioning. Display horizontal
entry/stop/target levels and risk/reward bands over the available chart viewport, plus a
deadline label. Do not fabricate future OHLCV bars or interpolate future x positions by
elapsed seconds just to draw an eight-week projection. Decorative future trajectory
arrows are outside the first release. Hide incompatible comparison/basis views honestly.

Ledger adds an explicit view selector: **Calls / Chart forecasts / Comparison**. Forecast
rows show symbol, originating model, publication date, entry state, targets/stop state,
planned-risk R, eight-week outcome and data health. An inspector holds the full original
setup, source references, timeline, paired answer and amendments. Clicking a chart level
or Ledger row reaches that same inspector. Phone views prioritize status and outcome;
details stay in the existing overlay pattern, not nested tables inside chat.

## Implementation slices and verification gates

No product implementation is authorized by this plan-only request. Once build is approved,
land these as coherent commits, with the feature unavailable until its required contracts
and evaluators exist. Intermediate fixtures stay synthetic and offline.

| Slice | Deliverable and likely homes | Gate |
| --- | --- | --- |
| 1. Contracts and evidence | `forecasts/models.py`, `store.py`, chart-store schema/retention/capacity; ticker cache provenance through shared render inputs | Strict validation, idempotent admission, foreign-key retention, overflow rollback, no refetch/substitution, wrong-session rejection |
| 2. Evaluation core | `forecasts/evaluator.py`, `candles.py`, `report.py`; reuse shared history/calendar/split transforms | Synthetic golden cases for both directions, every entry/exit/gap/ambiguity/deadline rule and split/revision handling |
| 3. Manual request to plotted forecast | `orchestrator/market_forecasts.py`, tool handler, `host/rpc_market_forecasts.py`, WS client, compact request sheet, forecast overlay and inspector | One manual request → real harness/structured submit → saved forecast → paint receipt → exact inspected evidence; no incidental run or scan |
| 4. Automatic tracking and Ledger | Scan post-price hook, focused schedule admission, Ledger report composition and forecast rows | Offline multi-day replay, restart/catch-up, gaps, duplicate scans, partial exits, horizon scoring and no LLM calls during tracking |
| 5. Paired comparison | Typed chart binding in shared lane runner, isolated sessions, directional prompt, matched report | Both lanes receive matching allowed evidence; no answer leakage/history imbalance, same publication clocks, partial failure/abort/retry behavior, usage attribution |
| 6. Product verification | Extend offline browser verifier and synthetic screenshots; frontend checks, backend integration and documentation | End-to-end story on desktop and 320/390px phones; full forecast/ledger/evidence flow, compact composer retained, operator-data sweep before push |

Keep modules small. `ledger.py` is already 414 lines; new evaluation belongs in
`forecasts/`. If changes to the existing ledger are required, first extract its scoring
concern without changing original semantics. Use `rpc_dispatch.py` for routing and a
focused RPC handler map, not additional business logic in `ws_server.py`.

Mandatory evaluator cases: opening versus intrabar entry; same-bar entry/exit uncertainty;
opening gap through stop; opening gap past setup; one/multiple/partial targets; long/short
symmetry; exact equality; entry expiry with no fill; deadline after partial realization;
stop before later recovery; publication midday/weekend/holiday/early close; stale fetch;
missing session; delayed evaluation at four/eight weeks; split normalization; revised
consumed history; repeated/reordered ingestion; and out-of-scope asset.

Mandatory integration cases: frozen levels survive drag/undo/amendment; hidden or failed
paint never changes score; closed/reopened page and restarted host converge; model cannot
select request owner/provider/publication time; unrelated sessions and excluded account
resources remain inaccessible; scan scope change requires current admission; partial
provider failure cannot rerun or silently complete a pair; every displayed result resolves
to exact persisted evidence; old ledger fixtures produce unchanged historical reports.

Completion requires a synthetic example where the trade stops out early, the price later
recovers, and the Ledger correctly displays a losing simulated trade alongside a correct
eight-week directional call. A second example must remain ambiguous rather than being
counted as a win. These are the key product truths, not optional edge-case polish.

## Decisions for the build

Recommended defaults above are proposals, not shipped behavior. The one founder preference
raised during planning is whether to enable paired comparison for each manual request;
the plan supports an explicit option and recommends it when evaluating improvement. It
costs one additional model run, so single-run mode remains available.

Recommended build order is contracts/evaluator first, followed immediately by the manual
request-to-chart vertical slice. Ship the full first release only after tracking, Ledger
integration and the selected comparison mode pass the acceptance story. Broader historical
ledger correction, intraday execution fidelity and crypto integration are separate work.
